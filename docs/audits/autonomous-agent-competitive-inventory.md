## Key Findings

1. GoodVibes has many raw foundations already: providers, channels, memory, routines, schedules, MCP, tasks, remote, artifacts, knowledge, media, permissions, and operator APIs.
2. The largest gap is not raw capability count. It is UX integration. Many OpenClaw, Hermes, and Odysseus features already exist in GoodVibes TUI, the connected daemon, or the SDK; Agent should expose those capabilities through user-first routes instead of reimplementing them.
3. The current Agent policy overcorrects against hidden work. The best-in-class target is visible autonomy: jobs can run unattended only when they have clear owner, scope, schedule, status, logs, and cancel/recovery routes.
4. Fresh provider-backed email/calendar records, browser-backed deep research runners, measured local model serving beyond confirmed model-list smoke checks, typed PTY process APIs, sudo credential mediation, external memory-provider execution/status records beyond the current setup contract maps, and first-class browser/desktop-control adapters are the clearest product gaps.
5. GoodVibes can lead on safety if it keeps its approval, redaction, trust, readiness, and release-evidence posture while removing unnecessary ceremony from approved workflows.

## Product Direction

- Present one assistant. Summary and visible TUI Home now start with the same assistant lanes; keep package/host ownership language in diagnostics.
- Make setup complete the user's outcome: installed, reachable, authenticated, paired, and ready to act. The current visible Start checklist covers connected-host auth and install smoke alongside runtime/model setup, and setup posture exposes a guided wizard with progress, current-step routes, saved checkpoint resume, checkpoint auto-advance evidence, backtracking routes, setup-smoke rerun/save routes, repeated-blocker focus from saved smoke history, live probe-fed connected-host diagnostics/status recommendations, token-safe connected-host auth posture with exact pairing route ids, confirmed SDK-backed local token create/repair without raw-token output, confirmed service repair routes with success criteria, serviceLifecycleDecision receipt gates, certified install/start/restart receipt outcomes, exact install/start/restart/no-action decisions from services.status receipts, offline GoodVibes host bootstrap commands before the operator endpoint is reachable, confirmed token-safe setup smoke execution with durable redacted evidence artifacts from package binary to first assistant turn plus Home/setup latest-result and history/trend surfacing, primary handoff cards from each actionable row to the safest visible form, diagnostic, or confirmed route, and a `setupCloseout` decision that turns critical blocker, saved smoke, and user completion-marker evidence into blocked, run-smoke, finish-setup, or complete states with the confirmed `onboarding-apply-close` route.
- Prefer supervised local execution over refusal or delegation friction when the Agent has local permission and workspace context; use `execution_posture`, `background_processes`, and `setup_item setupItemId:"sudo-execution-posture"` to make foreground, long-running, and privilege-escalation boundaries explicit.
- Use delegation and remote runners for isolation, parallelism, or remote execution, not because the user picked the wrong entrypoint. Keep the handoff brief explicit: original ask, reason, success evidence, workspace/worktree hint, priority, review intent, status route, and recovery path.
- Keep schedule edits explicit, exact-id, and previewed with read-only current-state diffs before confirmation.
- Extend live autonomy queue records with true host output chunk streams when the connected host exposes them beyond the current bounded task output route/preview descriptors.
- Promote certified watcher receipts into persisted queue/run history and provider-specific Gmail/email source records when the daemon publishes durable watcher source records.
- Attach fresh provider-backed email/calendar thread and event queues with confirmed send/edit/RSVP/archive execution once connector or daemon records expose durable provider ids, then deepen Personal Ops task and reminder queues with provider-backed records beyond the current local/connected-host operation cards.
- Keep learning consolidation explicit: preview duplicate groups, merge survivor fields, stage stale duplicates, delete only after stale, and rollback merge/stale phases through durable receipts.
- Promote external memory-provider setup/status/read/write/sync records into durable receipts when the connected host or SDK publishes concrete provider contracts, while keeping prompt receipt drill-in and outcome filtering raw-body-free.
- Turn research from the current visible run ledger, route planner, browser-runner contract, source queue, citation checks, and saved visual report packets into a browser-backed live report workflow with artifacts, cancellation, browser/PWA report rendering, and explicit knowledge ingest.
- Keep VIBE.md profile starter portability and project context inspection visible in profile authoring docs and release evidence as profile workflows evolve.
- Make browser, mobile, voice, and device control setup discoverable and repairable from the same assistant cockpit; the connected browser cockpit route is now visible through `ui_surfaces`, `open_ui_surface`, service posture, Home workspace discovery, and Voice & Media readiness, `pairing_posture` returns a device capability map that distinguishes ready published routes from camera/location contracts that are not yet published, and `media_posture` now maps explicit voice workflows without claiming wake-word capture.
